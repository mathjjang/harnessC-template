# ADR-261116-record-human-owner: 기록 머리에 담당 사람을 남긴다 — 생성기가 넣고 lint가 검사

- 상태: Accepted
- 작성: Claude Code (claude-fable-5-2) · 담당 mathjjang · 2026-11-16
- 강제 등급: generate + gate — 집행 수단: `.harness/catalog.yaml` new-doc.mjs(담당을 넣는다 · 모르면 거부) · lint.mjs ⑤(시작일 뒤 기록에 담당이 없으면 실패)
- 위험: low
- 선행 RFC: 없음
- 관련: HARNESS §8 귀속 · automation ADR-261116-record-human-owner(프로젝트 규칙으로 먼저 시험 — 기계 강제가 없어 사용자 "탬플릿 수정을 해야 해. 이건 중요해")
- 정책 소유: technical

> ADR은 되돌리기 비싼 결정에만 쓴다. 결정은 단정문으로. 대안이 비면 "정말 비교했나"를 의심한다.

## 1. Context (왜 지금)

- 귀속 머리는 `작성: <에이전트(모델)> · <날짜>`다. 에이전트는 남지만 그 세션을 돌린 사람은 남지 않는다.
- 개발자가 한 명일 때는 문제가 없었다. 둘 이상이 각자 PC · 각자 계정으로 같은 저장소에 기록을 쌓으면, 문서만 읽어서는 누구의 작업인지 알 수 없다. 커밋 작성자와 PR 계정에는 남지만 기록 ID · 브랜치 이름 · `Co-Authored-By`에는 사람이 없다.
- 프로젝트 규칙 한 줄(에이전트가 `--agent`에 담당을 붙인다)로는 빠뜨려도 lint가 통과한다 — "사람이 읽어야 지켜지는 규칙".

## 2. Decision (무엇을 한다 / 하지 않는다)

- 귀속 머리는 `작성: <에이전트(모델)> · 담당 <사람> · <날짜>`다. 개정 이력 행의 에이전트 칸도 `<에이전트(모델)> · 담당 <사람>`.
- 담당 = 그 세션을 돌리는 사람. 값은 `--owner` → 환경변수 `HARNESS_OWNER` → 그 저장소의 `git config user.name`. 커밋 작성자와 같은 이름이라 `git log --author`와 기록이 맞는다.
- **생성(generate)**: `new-doc.mjs`가 귀속 값에 담당을 붙인다(기록 · 큐 · 핸드오프 응답 · 스펙 · 런북). 담당을 알 수 없으면 만들지 않는다(종료 2). `work.mjs promote` · `setup.mjs`도 같은 값을 붙인다(모르면 그대로 두고 lint가 잡는다).
- **게이트(gate)**: lint ⑤가 ID 날짜(YYMMDD)가 시작일부터인 기록의 작성 줄에 담당이 있는지 본다. 시작일은 코어 기본 261117, 프로젝트는 `harness.yaml` `ids.owner_from`으로 바꾼다(늦게 동기화한 프로젝트가 사이 기록을 면제하는 자리). standard FDR은 `01-spec.md`의 작성 줄을 본다.
- 순서는 에이전트가 먼저, 담당이 그 뒤. `ci.mjs`는 `작성:` 뒤 첫 `·` 앞까지를 작성자로 읽어 리뷰어와 견준다 — 담당을 앞에 두면 그 검사가 틀어지므로 lint가 그 꼴을 담당 없음으로 본다.
- 하지 않는 것: 시작일 앞 기록을 고치지 않는다. 협업 저장소에 만드는 기록(MTG · DEC — 다른 조직이 본다)에는 담당을 붙이지 않는다. 기록 ID · 브랜치 이름에 사람을 넣지 않는다. 템플릿 파일(`{{AGENT}}`)은 그대로 — 값이 바뀔 뿐이다.
- 검사하지 않는 것: 담당 값이 실제 그 사람인지, 큐 항목 · 핸드오프 응답 · 개정 이력 행의 담당(생성기가 넣지만 lint는 기록 머리만 본다).

## 3. Alternatives

| 대안 | 장점 | 탈락 사유 |
|---|---|---|
| 프로젝트 규칙 한 줄(에이전트가 `--agent`에 붙임) | 코어 변경 없음 | 빠뜨려도 통과 — 기계 강제 없음 |
| 템플릿마다 `담당:` 줄을 따로 추가 | 줄이 분명하다 | 템플릿 30여 곳 · 손으로 만든 머리(setup ADR · qa-intake)까지 고쳐야 한다. 값 하나에 붙이면 한 곳 |
| 담당 = GitHub 로그인(`gh api user`) | 계정과 일치 | GitHub · gh · 네트워크에 의존 — 모든 프로젝트에서 같게 동작하지 않는다 |
| 기록 ID · 브랜치에 사람 접두 | 목록에서 바로 보임 | ID 규칙 변경 — 기존 링크 · 경로 매칭 전부에 닿는다 |
| 시작일 없이 모든 기록 검사 | 설정 없음 | 기존 기록 전부가 실패 — 역사를 고치게 만든다 |

## 4. Consequences (득실 · 후속 작업 · 되돌릴 때 비용)

- 득: 기록 한 장만 읽어도 누구의 작업인지 안다. 인자를 잊어도 생성기가 넣고, 손으로 만든 기록은 lint가 막는다.
- 실: `git config user.name`이 없는 환경(새 PC · CI에서 기록 생성)은 `--owner`나 `HARNESS_OWNER`를 줘야 한다. 이름을 바꾸면 같은 사람이 두 이름으로 남는다.
- 릴리스 노트: 설정 변경 없음(기본 시작일 261117). 그날 뒤에 만든 담당 없는 기록이 있는 프로젝트만 `ids.owner_from`을 동기화한 날로 적는다.
- 되돌릴 때: lint ⑤의 담당 검사와 생성기의 붙이기를 뺀다. 이미 적힌 담당은 그대로 둔다(작성자 해석에 영향 없음).
